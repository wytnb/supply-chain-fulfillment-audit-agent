# 规则编号：FSR-TP-001
# 规则名称：运输超时扣罚结算规则
# 知识库：`kb_freight_settlement_rules`
# 适用场景：`tracking_stagnation`
# 适用角色：`finance`、`logistics`、`manual_review`
# 规则版本：`v1.0`
# 是否模拟规则：`true`
# 关联测试编号：`RAG-MVP-003`、`RAG-EXT-002`

## 规则摘要
本规则用于回答“运输超时后是否可以进入结算扣罚，以及扣罚结果应如何被解释和留痕”。规则只解释结算口径和前置条件，不把文本写成数值计算来源。超时时长、宽限、封顶、扣罚金额均以 Settlement 工具读取结构化字段后的结果为准。  
根据系统设计，`settlement_calculate_timeout_penalty` 的数据来源是 `shipments.json`、`carriers.json` 与 `fee_rules.json`；其中 `packages.json` 又决定是否存在偏远地区附加条件。因此，结算规则的核心不是“凭经验扣多少”，而是“是否具备完整、可复核的结构化输入”。  
D03 样例说明了典型链路：运输停滞先由物流场景识别，再由 Settlement 工具输出超时与扣罚建议，并同步到异常工单。该链路证明扣罚结论属于结算输出，不属于承运商 SLA 文本本身。

## 触发条件
- `tracking_stagnation` 主规则已判定运单超过结构化 SLA 或存在明确运输超时。
- 财务或物流发起“是否应扣承运商款项”的结算复核。
- `fee_rules.json` 中能找到承运商与服务等级对应的超时扣罚规则。
- 运单未进入取消、无效、未发货等不适用状态。
- 如涉及偏远地区，已先按偏远地区前提规则完成校验。

## 需要查询的数据
- `shipments.json`：确认运单状态、发货时间、签收状态。
- `tracking_events.json`：确认轨迹停滞事实与最后节点。
- `carriers.json`：确认承运商服务等级对应的结构化 SLA。
- `fee_rules.json`：确认超时扣罚宽限、单价、封顶等参数是否存在。
- `packages.json`：确认是否偏远地区，以决定是否需要先走扩展前提校验。
- `exception_tickets.json`：确认是否已有物流异常工单和催办记录。
- 必要工具：`tms_check_tracking_stagnation`、`settlement_calculate_timeout_penalty`、`ticket_get_ticket_status`、`ticket_append_process_record`。

## 判断逻辑
- 第一步，必须先确认“超时事实成立”。若只是客户催促、但尚未超过结构化 SLA，不进入扣罚。
- 第二步，扣罚金额只能由 `settlement_calculate_timeout_penalty` 计算，RAG 文本仅说明应读取 `fee_rules.json` 中对应参数。
- 第三步，若承运商、服务等级或运单资料对不上，不允许直接出扣罚建议，应标记数据冲突并转人工复核。
- 第四步，偏远地区单据必须先完成扩展 SLA 校验。未经偏远地区前提校验得出的普通区域扣罚结论，不可直接落账。
- 第五步，若运单已同时进入赔付争议、异常签收或账单争议，扣罚建议应单独留痕，不与赔付金额在文本中合并解释。
- 第六步，若账单已生成但尚未确认，可作为对账异议依据；若账单已确认，则只能输出“复议/追补建议”，不能在规则中宣称已自动扣回。

## 责任归因
- 超时事实的业务责任由 `logistics` 提供证据和跟进记录。
- 是否落入扣罚结算、如何入账或冲账，由 `finance` 负责。
- 规则缺失、数据冲突、偏远地区属性不清等情况归入 `manual_review`。
- 客服不参与扣罚结算决策，只能同步“内部已复核”。

## 处理建议
- 先保留轨迹停滞证据，再调用 Settlement 工具试算，不要仅凭工单主观描述发起扣罚。
- 将承运商、服务等级、偏远标记、最后轨迹摘要一起写入结算备注，便于财务复核。
- 若已有物流异常工单，建议在原工单中追加“已进入扣罚评估”记录，并关联财务复核工单。
- 输出结论时使用“建议扣罚”“满足扣罚前提”“需人工复核”这类分级表达，不使用“已扣款成功”。
- 如 Settlement 结果命中封顶或特殊参数，也只说明“由结构化费规计算得出”，不在规则正文展开数值。

## 升级条件
- `fee_rules.json` 找不到适用规则，导致 Settlement 工具无法稳定计算。
- 同一运单存在多个承运商或服务等级口径冲突。
- 财务准备据此与承运商对账，但物流侧未补齐催办或异常证据。
- 偏远地区、异常签收、赔付审核与超时扣罚同时发生，单一结论不足以支撑入账。
- 账单已经确认，需发起异议重审或补充追扣。

## 客服表达建议
- 对客通常无需展开扣罚规则，可统一表述为：该单异常已转内部物流与结算团队继续核查。
- 如客户追问处理进度，可表述为：我们已对承运链路发起内部复核，当前以尽快定位并推进处理为主。
- 不建议向客户披露内部扣罚标准、金额算法和承运商对账策略。
- 不建议把“内部扣罚”表述成客户一定获得赔付的依据。

## 工单字段建议
- `scenario_code`：`tracking_stagnation`
- `exception_type`：`tracking_stagnation`
- 建议新增结算子字段：扣罚前提是否成立、是否偏远地区、是否已完成 Settlement 试算
- 关键依据字段：`carrier_code`、`service_level`、最后轨迹类型、异常工单号、Settlement 结果摘要
- 财务协同字段：账单状态、是否待对账、是否需复议
- 风险标记：规则缺失、数据冲突、需人工确认
