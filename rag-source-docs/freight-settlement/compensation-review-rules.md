# 规则编号：FSR-CR-002
# 规则名称：赔付审核与结算承接规则
# 知识库：`kb_freight_settlement_rules`
# 适用场景：`abnormal_signed`、`damage_or_loss_compensation`
# 适用角色：`finance`、`customer_service`、`logistics`、`manual_review`
# 规则版本：`v1.0`
# 是否模拟规则：`true`
# 关联测试编号：`RAG-MVP-004`、`RAG-EXT-001`

## 规则摘要
本规则定义赔付审核何时可以从异常判断进入结算承接，重点解决“证据是否完整、赔付条件是否具备、是否必须人工确认”。它适用于当前已落样的 `abnormal_signed`，也为后续扩展场景 `damage_or_loss_compensation` 预留统一审核入口。  
根据设计文档，赔付类场景必须先查 `kb_freight_settlement_rules` 与 `kb_carrier_sla_rules`，需要补充异常归因时再查履约异常规则。这意味着结算规则在这里承担的是“受理与审核”职责，而不是先给金额。金额建议来自 `compensation_cases.json` 或 Settlement 工具，RAG 只解释何时可用、何时不可直接采用。  
当前 mock 数据已经体现核心边界：异常签收赔付案存在、承运商支持赔付，但证据状态仍待客户补充，且案例要求人工确认。由此可见，赔付审核的关键门槛是证据完备度，而非系统里是否已经有建议赔付金额。

## 触发条件
- 已识别为 `abnormal_signed`，且客服或物流需要判断是否进入赔付审核。
- 用户发起破损、丢件、未收到货等索赔诉求，需要统一进入结算判断。
- `compensation_cases.json` 已存在相关案例，或业务需要创建赔付审核草案。
- `carriers.json` 显示承运商支持赔付，或虽未明确支持但需要人工复议。
- 财务需要确认案件是“继续补证”还是“可进入结算审批”。

## 需要查询的数据
- `compensation_cases.json`：确认 `case_no`、`exception_type`、`evidence_status`、`manual_confirm_required`、建议赔付字段。
- `shipments.json`：确认签收状态、签收凭证、异常原因，尤其适用于异常签收类。
- `tracking_events.json`：确认最后节点和异常发生链路。
- `orders.json`、`order_items.json`：确认订单有效、商品明细、商品金额基础，用于赔付审核留档。
- `packages.json`：确认是否存在 `fragile_pack` 等增值服务，作为审核风险补充。
- `carriers.json`：确认承运商是否支持赔付。
- `exception_tickets.json`：确认是否已有异常签收工单、赔付跟进记录或人工复核记录。

## 判断逻辑
- 第一步，先确认案件属于可赔付审核的异常类型。当前明确支持 `abnormal_signed`；`damage_or_loss_compensation` 作为扩展场景沿用同一审核入口。
- 第二步，检查是否已有赔付案例。已有案例时优先续用原案例状态，不重复生成互相冲突的赔付结论。
- 第三步，若 `evidence_status` 显示待补证，或者 `manual_confirm_required` 为真，结论只能是“进入赔付审核中”，不能输出最终赔付通过。
- 第四步，异常签收类至少要同时具备签收凭证、客户未收到货主张、承运商派送说明三类材料后，才能进入最终结算确认。
- 第五步，破损或丢件类虽在当前 mock 数据中未落完整样例，但按同一口径应补齐货损照片/开箱证明、商品明细与价值凭证、包裹交接或运输异常证据后再审。
- 第六步，即便系统中已有建议赔付金额，也只能把它视为“结构化建议值”，仍需经过人工确认、证据核验和责任归因复核。
- 第七步，若承运商不支持赔付或证据链明显冲突，规则应输出“需人工协商/复议”，而不是直接否赔或直接赔付。

## 责任归因
- `customer_service` 负责接收索赔诉求并补齐客户侧证据。
- `logistics` 负责调取承运商底单、轨迹说明、交接记录和派送解释。
- `finance` 负责在证据完整后作赔付审核、结算记账和后续对账处理。
- 证据缺失、事实冲突、金额敏感或多异常并发时，先归入 `manual_review`。
- 若案件同时涉及异常签收和超时扣罚，二者可并行复核，但不在同一条规则结论中互相替代。

## 处理建议
- 对已存在的赔付案例，优先更新证据状态和人工审核状态，不新建平行案例。
- 输出时明确区分“可受理索赔”“证据待补齐”“可进入结算审批”“需人工复议”四类状态。
- 不把 `compensation_amount` 直接当最终赔付承诺；应注明其为结构化建议值或工具试算结果。
- 对破损、丢件扩展场景，建议沿用同样的案例字段框架，保证后续 Settlement 与工单体系可复用。
- 若商品存在 `fragile_pack` 等易损包装增值服务，应提高人工复核优先级，因为这类服务会影响责任说明和争议判断。

## 升级条件
- 客户证据、承运商证据、结构化签收事实之间相互矛盾。
- 赔付案例长时间停留在待补证状态，可能错过承运商争议窗口。
- 同一订单同时出现异常签收、破损、丢件等多重索赔主张。
- 财务准备结算，但客服和物流尚未完成补证闭环。
- 承运商拒赔、规则不明确或建议赔付金额与业务认知差异过大。

## 客服表达建议
- 可表述为：案件已进入赔付审核流程，我们正在同步核验签收/运输证据，待材料完整后再给出最终处理结果。
- 可表述为：目前系统已有赔付审核记录，但仍需补充必要证明并经过人工确认。
- 不建议表述为：系统显示有金额，所以一定会赔。
- 不建议在证据未齐时承诺赔付方式、到账时间或最终责任比例。

## 工单字段建议
- `scenario_code`：`abnormal_signed` 或 `damage_or_loss_compensation`
- `exception_type`：按实际使用 `abnormal_signed`、`damage_compensation_review`、`lost_package_compensation_review`
- `responsible_department`：初始建议 `manual_review`
- 关键赔付字段：`case_no`、`evidence_status`、`manual_confirm_required`、是否承运商支持赔付
- 证据字段：客户举证清单、承运商举证清单、签收/破损/丢件图片或说明链接
- 结算字段：建议赔付来源、是否已进入财务审核、是否需与账单或扣罚联动
