# 知识库：kb_fulfillment_exception_rules
# 适用场景：damage_or_loss_compensation
# 适用角色：customer_service、logistics、manual_review、finance
# 规则版本：v1.0
# 是否模拟规则：true
# 关联测试编号：RAG-EXT-001

## 规则摘要
本规则用于解释破损、丢件或未收到货的扩展赔付场景中，异常应如何做初步归因，以及何时把案件从“客户主张”推进为“可进入赔付审核的异常事件”。  
在当前仓库里，`damage_or_loss_compensation` 仍属于扩展验证场景，因此本规则重点提供统一的归因入口：先确认订单和运单是否有效，再确认问题类型是破损、丢件、异常签收后未收到，最后判断证据是否足以进入结算审核。  
本规则只做归因，不直接输出赔付金额，也不直接替代承运商 SLA 或结算审核规则。

## 触发条件
- 用户明确提出破损、丢件、少件、未收到货并要求赔付。
- 订单或运单可被定位，且仍能关联到履约与运输记录。
- 需要把案件纳入赔付审核或异常工单流转。
- 已存在赔付案例，或需要创建赔付审核草案。
- 需要区分问题是签收争议、运输丢件、货损还是证据不足。

## 需要查询的数据
- `orders.json`：确认订单有效、商品范围和订单金额背景。
- `shipments.json`：确认运单状态、签收状态和异常原因。
- `tracking_events.json`：确认运输链路是否完整，是否在某个节点后失联或异常签收。
- `compensation_cases.json`：确认问题类型、证据状态、是否要求人工确认。
- `order_items.json`：确认商品明细，辅助界定破损或丢失范围。
- `exception_tickets.json`：确认是否已有相关工单和历史处理记录。

## 判断逻辑
- 第一步，先确认用户主张对应的是哪类异常。破损强调商品状态问题，丢件强调运输或签收后无法找回，异常签收后未收到则优先进入签收争议链路。
- 第二步，若系统已有赔付案例且仍待补证，说明当前只能进入审核准备状态，不可直接给出赔付结论。
- 第三步，若运单显示正常签收、客户也确认已收到，仅反馈商品受损，则归因方向更偏向货损而非丢件。
- 第四步，若运单在运输中失联且无签收事实，可优先视为丢件风险，但仍需后续 SLA 和结算规则补充。
- 第五步，若问题类型、签收状态和客户说明互相冲突，应标记为 `manual_review`，避免过早定义责任。
- 第六步，本规则输出的是“是否可进入赔付审核、当前异常更接近哪种类型”，而不是最终赔付结论。

## 责任归因
- 客服负责接收诉求与初步分类，但不承担最终责任认定。
- 物流负责补齐运输、签收和承运商侧证据。
- 财务负责后续赔付审核与结算承接，不在本规则中给金额。
- 证据不足、事实冲突或多异常并发时，先归入 `manual_review`。

## 处理建议
- 先将案件归入“破损”“丢件”“异常签收后未收到”中的一个主方向，避免多口径并行。
- 若已有赔付案例，优先在原案例上更新证据状态，不新建平行案例。
- 指导前线按场景收集证据，例如商品问题说明、未收到说明、签收争议说明或运输异常说明。
- 对客户只说明“已进入审核准备或补证流程”，不承诺赔付结果。
- 证据齐备后再转交承运商 SLA 和结算规则继续处理。

## 升级条件
- 证据链长期不完整，影响后续赔付判断。
- 问题类型在破损、丢件、异常签收之间反复变化，无法稳定归类。
- 客户要求立即给出赔付结论或金额。
- 承运商说明、客户说明和结构化状态明显冲突。
- 同一订单出现多重索赔主张，需要统一进入人工复核。

## 客服表达建议
- 可表述为：您的问题已进入赔付审核准备流程，当前需要继续核对相关事实和证据。
- 可表述为：我们会先按异常类型整理处理方向，最终结果以人工复核为准。
- 不建议表述为：一定全赔、一定拒赔、今天就能处理完。

## 工单字段建议
- `scenario_code`：`damage_or_loss_compensation`
- `exception_type`：按实际使用 `damage_compensation_review` 或 `lost_package_compensation_review`
- `responsible_department`：优先 `manual_review`
- 建议补充字段：`order_no`、`waybill_no`、问题类型、`evidence_status`、`manual_confirm_required`、是否已有赔付案例、客户补证状态
