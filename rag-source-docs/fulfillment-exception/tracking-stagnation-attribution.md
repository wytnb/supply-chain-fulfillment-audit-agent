# 规则编号：FE-003
# 规则名称：运输停滞异常归因补充规则
# 知识库：kb_fulfillment_exception_rules
# 适用场景：tracking_stagnation
# 适用角色：logistics、customer_service、manual_review
# 规则版本：v1.0
# 是否模拟规则：true
# 关联测试编号：RAG-MVP-003

## 规则摘要
本规则用于补充 `tracking_stagnation` 的异常归因视角，说明“轨迹停滞为什么被视为异常，以及何时需要从运输异常升级为人工跟进”。  
主规则中的 SLA 判定由 `kb_carrier_sla_rules` 负责，本规则不重复解释 SLA 数值，而是解释异常类型、责任边界和跟进动作。其作用是帮助系统把“轨迹长时间无更新”从普通运输中区分出来，并形成可操作的工单和对客口径。  
本规则只处理在途停滞，不处理已签收争议、赔付审核或账单审核。

## 触发条件
- 运单已建立且已发货。
- 用户以 `waybill_no` 或订单关联运单发起“物流不动”“停在某一站点”“很久没更新”的查询。
- `tracking_events.json` 中最后轨迹停留在运输节点，后续未见有效更新。
- `shipments.json` 中运单仍未完成正常签收。
- 需要把异常从普通运输跟踪提升为物流侧重点跟进事件。

## 需要查询的数据
- `shipments.json`：确认运单状态、发货时间、签收状态。
- `tracking_events.json`：确认最后轨迹时间、最后轨迹类型和停留节点。
- `exception_tickets.json`：确认是否已有物流异常工单和历史跟进动作。
- `carriers.json`：仅用于确认承运商与服务等级，不在本规则中承担数值口径。

## 判断逻辑
- 第一步，先确认运单是否真实发出。未发货的单据不能被定义为运输停滞。
- 第二步，确认最后轨迹是否仍属于运输节点，如揽收、中转、离开发运中心、延迟扫描、待派送等。若已进入签收节点，应切换到异常签收逻辑。
- 第三步，观察轨迹是否形成连续停顿，即长时间没有新的运输事件，且当前状态无法解释包裹下一步动作。
- 第四步，若系统已存在相关工单，且工单仍处于 `OPEN` 或持续催办状态，则说明异常已被识别，但仍未解决；此时应继续跟进而非重复建单。
- 第五步，若轨迹缺失、运单状态冲突或物流状态与工单记录不一致，应输出“数据冲突，需人工复核”。
- 第六步，本规则只解释停滞为何构成异常，不把超时扣罚、偏远地区扩展条件写入本篇；这些属于扩展或结算规则。

## 责任归因
- 在途停滞的主责通常为 `logistics`，因为问题发生在仓外运输链路。
- 客服负责对客同步和信息回收，但不承担主责认定。
- 若运单状态、轨迹状态和签收状态相互冲突，应暂时归入 `manual_review`。
- 财务只在后续进入扣罚或对账复核时参与，不在本规则主判中承担责任。

## 处理建议
- 先提炼异常摘要，例如“运单仍在运输中，最后轨迹停留在转运或延迟扫描节点，后续无更新”。
- 向物流团队发起催办，要求承运商补充当前处理状态和下一步节点说明。
- 将最后轨迹时间、最后轨迹类型、承运商、服务等级写入异常工单，便于持续跟进。
- 若客户已投诉，应将案件优先级提升，但仍保持“等待承运商核查”的口径。
- 如后续确认存在扣罚前提，再转交 SLA 扩展规则和结算规则处理。

## 升级条件
- 运单长期未恢复轨迹更新。
- 已有工单仍未关闭，且承运商多轮催办后无有效反馈。
- 客户多次追问或投诉，继续等待会导致服务风险。
- 最后轨迹为明显异常节点，如延迟扫描、长期停留中转、派送前反复无变化。
- 结构化数据之间存在冲突，无法稳定确认案件当前状态。

## 客服表达建议
- 可表述为：包裹已进入运输链路，目前物流节点更新异常，相关团队正在继续核查和催办。
- 不建议表述为：已经丢件、承运商一定全责、肯定会赔。

## 工单字段建议
- `scenario_code`：`tracking_stagnation`
- `exception_type`：`tracking_stagnation`
- `responsible_department`：`logistics`
- `ticket_type`：`logistics_exception_ticket`
- 建议补充字段：`waybill_no`、`carrier_code`、`service_level`、最后轨迹时间、最后轨迹类型、最后轨迹城市、是否已有历史催办
