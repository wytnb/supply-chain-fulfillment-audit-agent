# 规则编号：CSLA-TS-001
# 规则名称：运输轨迹停滞判定与升级规则
# 知识库：`kb_carrier_sla_rules`
# 适用场景：`tracking_stagnation`
# 适用角色：`logistics`、`customer_service`、`manual_review`
# 规则版本：`v1.0`
# 是否模拟规则：`true`
# 关联测试编号：`RAG-MVP-003`

## 规则摘要
本规则用于回答“运单是否已进入承运商运输停滞状态，以及是否应由物流侧立即催办升级”。规则只负责解释停滞判定、责任归因和升级前提，不直接给出承运商 SLA 数值，也不直接产出扣罚金额。  
依据仓库设计口径，`tracking_stagnation` 的主规则应优先落在承运商 SLA 判断：先确认运单已真实发出、当前仍处于运输中，再结合承运商与服务等级对应的结构化 SLA 判断是否超过时效，并检查最后一条轨迹是否长时间没有更新。  
在当前 mock 数据中，D03 样例体现了典型在途停滞：运单未签收、仍处 `IN_TRANSIT`，最后轨迹为延迟扫描类事件，且系统已存在物流异常工单。该口径说明停滞判断不仅看“没送达”，还要看“轨迹更新链路是否断续或停住”。

## 触发条件
- 用户输入运单号，诉求集中在“物流不动”“很久没更新”“是否超时”。
- 已通过 `tms_get_shipment_detail` 或 `tms_get_waybill_by_order` 定位到有效运单。
- `shipment_status` 显示仍在运输流程中，且 `delivery_status` 不属于已完成正常签收。
- `tms_check_tracking_stagnation` 返回命中，或人工根据 `tracking_events.json` 能看到最后轨迹与当前基线时间之间已形成明显停滞。
- 未进入异常签收、赔付审核、账单审核等其他主场景的优先判定。

## 需要查询的数据
- `shipments.json`：确认 `waybill_no`、`carrier_code`、`service_level`、`shipment_status`、`ship_time`、`delivery_status`。
- `tracking_events.json`：确认最后轨迹时间、最后轨迹类型、最近城市节点、是否存在延迟扫描或转运停留描述。
- `carriers.json`：确认承运商与服务等级对应的结构化 SLA 来源。
- `exception_tickets.json`：确认是否已有 `tracking_stagnation` 相关工单、当前状态是否为 `OPEN` 或已被持续跟进。
- 建议工具：`tms_get_shipment_detail`、`tms_get_tracking_events`、`tms_get_carrier_profile`、`tms_check_tracking_stagnation`、`ticket_list_by_order`。

## 判断逻辑
- 第一步，先确认运单存在且已发货。未发货、已取消、已正常签收的单据不适用本规则。
- 第二步，确认最后一条轨迹是运输节点而非正常签收节点。若最后事件已是 `SIGNED`，应切换到异常签收或已签收复核逻辑。
- 第三步，以 `carriers.json` 中承运商与服务等级的结构化 SLA 作为唯一时效口径；RAG 只解释“要比对 SLA”，不在正文写具体时长。
- 第四步，同时观察轨迹内容本身。若最后轨迹表现为转运离场后无后续扫描、延迟扫描、长期停留在转运中心或派送前节点，可支持“停滞”结论。
- 第五步，若系统已有同运单的物流异常工单且状态未关闭，说明该异常已进入人工跟踪，应输出“继续催办并升级”的建议，而不是重新定义责任。
- 本规则只回答“是否停滞、是否需要升级”，不混入超时扣罚、偏远地区附加前提和金额结算；相关内容应转到扩展文档和结算规则文档。

## 责任归因
- 默认责任部门为 `logistics`，因为停滞发生在仓外运输链路，主责在承运商管理与物流跟进。
- 若 `shipments.json`、`tracking_events.json` 与工单状态互相矛盾，例如显示已签收但轨迹未完结，应先归入 `manual_review`。
- 客服可承担对客同步义务，但不是主责判定部门。
- 财务不参与本规则主判，只在后续进入扣罚或账单异议时接手。

## 处理建议
- 立即拉取最新轨迹并确认最后扫描节点是否停留在转运或派送前环节。
- 如已存在开放中的物流异常工单，优先在原工单追加催办记录，避免重复建单。
- 向承运商发起催办，要求补充当前包裹位置、下一节点 ETA 和延迟原因说明。
- 对内输出“已超过结构化 SLA 需升级跟进”或“尚未超过 SLA 但轨迹异常需持续观察”的分层结论。
- 如后续需要扣罚判断，转交 `timeout-penalty-rules`，不要在本规则内直接写扣罚结论。

## 升级条件
- 运单已命中停滞判断，且承运商未在本轮跟进后恢复轨迹更新。
- 最后一条轨迹属于延迟扫描、转运停滞或其他明显异常事件。
- 已存在 `OPEN` 状态物流工单，且多次催办后仍无恢复。
- 客户已发起催促或投诉，继续等待会影响承诺送达解释。
- 结构化数据冲突，导致系统无法确认当前是否仍在运输中。

## 客服表达建议
- 可表述为：包裹已进入承运商运输环节，目前物流节点更新异常，正在向承运商加急核实最新流转情况。
- 可表述为：当前系统显示尚未完成签收，我们已同步物流专员优先催办，并将在拿到承运商反馈后第一时间告知。
- 不建议表述为：一定丢件了、一定会赔、平台已经确认承运商全责。
- 不建议直接承诺具体到达时间，除非承运商已给出结构化或人工确认的下一步节点。

## 工单字段建议
- `scenario_code`：`tracking_stagnation`
- `exception_type`：`tracking_stagnation`
- `responsible_department`：`logistics`
- `ticket_type`：`logistics_exception_ticket`
- 关键证据字段：`waybill_no`、`carrier_code`、`service_level`、最后轨迹时间、最后轨迹类型、最后轨迹城市
- 跟进字段：是否已有历史催办、承运商反馈摘要、下一次回查时间
- 结算透传字段：是否需进入超时扣罚预审、是否存在偏远地区标记、是否已有关联账单
