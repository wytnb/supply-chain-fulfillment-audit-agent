# 规则编号：CSLA-AS-003
# 规则名称：异常签收举证与索赔时效规则
# 知识库：`kb_carrier_sla_rules`
# 适用场景：`abnormal_signed`
# 适用角色：`customer_service`、`logistics`、`manual_review`、`finance`
# 规则版本：`v1.0`
# 是否模拟规则：`true`
# 关联测试编号：`RAG-MVP-004`

## 规则摘要
本规则用于回答异常签收场景下“是否应进入举证索赔流程、当前证据是否足以提交结算审核、哪些节点必须在承运商争议时效内完成”。规则不直接给出赔付金额，但要求把签收凭证、客户主张和承运商反馈组织成可复核证据链。  
根据文档口径，`abnormal_signed` 的判责路由同时会访问履约异常、承运商 SLA 和运费结算规则。承运商 SLA 文档在这里承担的是“索赔时效与举证前提”的解释职责：先确认这是异常签收，再确认现有证据是否足以支持后续 Settlement 审核，而不是一收到客户投诉就直接认定赔付成立。  
当前 mock 数据已给出典型样例：订单对应运单显示 `ABNORMAL_SIGNED`，签收人为门卫代收，存在图片类签收凭证，异常原因是客户称未收到，且赔付案例状态仍为待补客户证据并要求人工确认。这说明异常签收的关键不是“有无签收”，而是“签收是否可被客户认可并能否形成完整索赔材料”。

## 触发条件
- 用户以订单号或运单号发起“已签收但未收到货”的投诉。
- `shipments.json` 中 `delivery_status` 为 `ABNORMAL_SIGNED`，或虽为已签收但签收信息与客户陈述明显冲突。
- `tracking_events.json` 最后事件已到签收节点，但签收人、签收方式、签收凭证需要复核。
- `compensation_cases.json` 已存在同单赔付案例，且证据状态未完备或需人工确认。
- 客服或物流需要判断是否还能继续向承运商追索。

## 需要查询的数据
- `shipments.json`：唯一签收状态与签收凭证来源，重点查询 `delivery_status`、`signed_time`、`signed_by`、`signed_proof_type`、`signed_proof_url`、`abnormal_reason`。
- `tracking_events.json`：确认签收前后的轨迹是否连续，最后一跳是否为代收、驿站、门岗等非客户本人场景。
- `orders.json` 与 `oms_get_order_address`：确认订单有效、地址脱敏信息与派送城市是否一致。
- `compensation_cases.json`：确认是否已有赔付申请、`evidence_status` 是否仍待补证、`manual_confirm_required` 是否为真。
- `carriers.json`：确认承运商是否支持赔付追索。
- `exception_tickets.json`：确认是否已有异常签收工单及客户投诉记录。

## 判断逻辑
- 第一步，先以 `shipments.json` 认定是否存在“签收事实”。没有签收事实的，不适用本规则，应转回运输停滞或丢件排查。
- 第二步，若存在签收事实，再看签收是否异常。代收、门岗代签、图片凭证但客户明确否认收货、异常原因字段已标识客户未收到，都可支持异常签收成立。
- 第三步，异常签收成立后，不等于赔付立即成立。必须同步核查客户证据是否已提交、承运商签收底单是否可调取、轨迹链路是否完整。
- 第四步，若 `compensation_cases.json` 显示证据待补或需人工确认，结论应是“允许进入索赔与赔付审核流程，但当前证据未完结”，而不是直接输出最终赔付。
- 第五步，只有在承运商支持赔付、客户与承运商双方证据都已收集到位时，才可把案件完整移交给运费结算知识库和 Settlement 工具继续审核。
- 本规则不写具体索赔时限数值，只强调“必须在承运商允许的争议时效内完成证据收集与提交流转”，其时间阈值以结构化或外部承运协议为准。

## 责任归因
- 客服负责收集客户未收到货的主张和补充证明，但不直接判定赔付成功。
- `logistics` 负责向承运商调取签收底单、派送说明和末端交接信息。
- `finance` 只在证据链齐备后进入赔付审核与结算处理。
- 当前证据未齐、双方陈述冲突或存在高风险争议时，责任部门先标记为 `manual_review`。
- 若结构化数据已明确正常本人签收且无异常原因，客户投诉不能直接推翻签收事实，应先人工复核。

## 处理建议
- 第一时间冻结“直接赔付”口径，改为“先核实签收凭证与客户收货情况”。
- 调取并留存 `signed_proof_url` 对应的签收凭证摘要，记录签收人身份信息描述。
- 要求客户补充未收到货说明、可用接收记录或现场证明，避免只凭口头陈述推进赔付。
- 若已存在赔付案例或异常签收工单，继续在原案例上补证，保持证据链闭环。
- 证据齐备后再调用 `settlement_calculate_compensation` 或进入 `compensation-review-rules`，不要在 SLA 文档中直接落金额。

## 升级条件
- 签收争议已进入承运商追索窗口，但客户或承运商证据仍未提交完整。
- 承运商拒绝提供签收底单、派送说明或交接记录。
- 客户连续投诉，且前线客服无法仅凭现有信息稳定解释。
- 运单同时存在异常签收与疑似破损/丢件争议，需要合并进入赔付审核。
- 结构化签收状态、客户陈述、工单记录三者互相冲突。

## 客服表达建议
- 可表述为：系统显示该单存在异常签收记录，我们已同步核查签收凭证并向承运商调取派送说明。
- 可表述为：当前案件已进入异常签收复核流程，待客户补充收货争议证明后，我们会继续推进赔付审核。
- 不建议表述为：已经确认丢件、一定全额赔、一定是承运商责任。
- 不建议要求客户重复多次提交相同材料，应一次性说明所需证据清单。
