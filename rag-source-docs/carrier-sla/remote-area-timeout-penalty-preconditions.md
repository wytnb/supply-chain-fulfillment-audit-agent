# 规则编号：CSLA-RA-002
# 规则名称：偏远地区超时扣罚适用前提规则
# 知识库：`kb_carrier_sla_rules`
# 适用场景：`tracking_stagnation`
# 适用角色：`logistics`、`finance`、`manual_review`
# 规则版本：`v1.0`
# 是否模拟规则：`true`
# 关联测试编号：`RAG-EXT-002`

## 规则摘要
本规则是 `tracking_stagnation` 的扩展规则，只回答“偏远地区运单在什么前提下可以进入超时扣罚判断”，不负责停滞主判，也不直接给出扣罚数值。  
根据仓库设计口径，偏远地区额外时效和超时扣罚参数都属于结构化数据范畴：是否偏远地区以 `packages.json` 为准，承运商基础时效及偏远地区附加时效以 `carriers.json` 为准，扣罚宽限与扣罚参数以 `fee_rules.json` 为准。RAG 文档只能解释这些字段之间的先后关系，不能把数值写成规则真源。  
因此，偏远地区单据不能因为“看起来送得慢”就直接扣罚，必须先完成偏远属性确认、服务匹配确认、扩展 SLA 重新比对，再决定是否把案件移交结算侧。

## 触发条件
- 用户或系统已将案件识别为 `tracking_stagnation`，并进一步询问“是否应扣罚”。
- 运单对应包裹存在偏远地区配送可能，或 `value_added_services` 中出现偏远配送类服务。
- `packages.json` 中 `is_remote_area` 为真，或业务明确要求核查偏远地区口径。
- 需要把物流超时结果移交财务/结算进行后续审核。
- 主规则已确认运输异常，但尚未确认是否满足扣罚前提。

## 需要查询的数据
- `packages.json`：确认 `is_remote_area` 是否为真，以及是否有偏远配送类增值服务。
- `carriers.json`：确认承运商基础 SLA 与偏远地区附加时效字段。
- `fee_rules.json`：确认超时扣罚是否存在宽限、是否存在封顶等结算侧参数。
- `shipments.json`：确认运单状态、发货时间、签收状态。
- `tracking_events.json`：确认最后轨迹和实际到达链路。
- `exception_tickets.json`：确认是否已有物流工单及催办记录。
- 建议工具：`tms_get_shipment_detail`、`tms_get_tracking_events`、`tms_get_carrier_profile`、`settlement_calculate_timeout_penalty`、`ticket_get_ticket_status`。

## 判断逻辑
- 第一步，只能以 `packages.json` 的 `is_remote_area` 作为偏远地区结构化真源，不能凭收货地址文字、地区印象或客服描述自行判断。
- 第二步，确认 `packages.json`、`shipments.json`、`carriers.json` 三者中的 `waybill_no`、`carrier_code`、`service_level` 能正确对齐；如不一致，不进入扣罚判断。
- 第三步，在承运商基础 SLA 上叠加偏远地区附加时效后，再判断是否真正超时。也就是说，偏远地区单据必须先“吃掉”允许的附加时效，不能沿用普通区域口径。
- 第四步，若已超过扩展后的承诺时效，还需继续检查 `fee_rules.json` 中是否存在超时扣罚适用参数；若该承运商服务等级没有对应规则，输出“规则不足，需人工复核”。
- 第五步，进入结算前要确认异常并非仅由偏远地区正常延长造成。若运单只是处于偏远地区合理配送窗口内，则只能继续跟踪，不应输出扣罚建议。
- 第六步，本规则不在文档里写具体小时数、每小时扣罚标准或封顶金额。金额相关结果必须由 Settlement 工具计算后再回填结论。

## 责任归因
- 偏远地区属性真实存在且已超过扩展 SLA 时，主责仍归 `logistics`，后续扣罚审核由 `finance` 接手。
- 若偏远地区标记缺失、包裹属性与承运商服务不匹配，先归入 `manual_review`。
- 若运单仍在偏远地区允许配送窗口内，不形成扣罚责任，仅保留物流跟进责任。
- 客服不负责确认偏远地区扣罚成立与否，只负责同步当前核查状态。

## 处理建议
- 先输出“是否满足偏远地区扣罚前提”，再决定是否调用结算工具，不要反过来先算钱。
- 命中前提时，将 `is_remote_area`、承运商服务等级、异常轨迹摘要一并透传给结算侧。
- 未命中前提时，应明确说明原因是“偏远地区时效扩展尚未扣除完”或“偏远地区标记不足，无法判定”。
- 对已有物流工单的案件，建议追加“是否满足结算扣罚前提”的审查记录，而不是另起无关联工单。
- 若后续承运商补传说明或修正远程区属性，应重新复核，不沿用旧结论。

## 升级条件
- 偏远地区标记、承运商服务等级或包裹资料出现冲突。
- 已超过扩展 SLA，但 `fee_rules.json` 找不到可适用的扣罚规则。
- 承运商已回应为偏远地区正常配送，但结构化标记与其说法不一致。
- 同一运单同时涉及停滞、异常签收或赔付争议，单一规则无法独立下结论。
- 财务要求落账扣罚，但物流侧证据链尚未齐备。

## 客服表达建议
- 可表述为：该单已进入偏远地区时效复核，我们正在按承运商服务标准确认是否属于正常延长配送范围。
- 可表述为：如确认超出偏远地区适用时效，我们会同步内部结算与物流团队继续处理。
- 不建议表述为：偏远地区一定不赔、偏远地区一定会扣承运商。
- 不建议向客户披露内部扣罚逻辑细节或金额口径。

## 工单字段建议
- `scenario_code`：`tracking_stagnation`
- `exception_type`：`tracking_stagnation`
- `responsible_department`：`logistics`
- 建议补充字段：`is_remote_area`、`value_added_services`、`carrier_code`、`service_level`
- 结算衔接字段：是否满足偏远地区扣罚前提、是否已调用 Settlement 试算、是否存在承运商反馈说明
- 风险标记：数据冲突、规则缺失、需人工复核
